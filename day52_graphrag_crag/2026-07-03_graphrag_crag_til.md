# 2026-07-03 TIL - GraphRAG와 Agentic RAG/CRAG

## 오늘 배운 내용

오늘은 기존 벡터 RAG의 한계를 보완하는 두 가지 흐름을 배웠다.

1. GraphRAG
   - 문서를 지식 그래프로 바꾸고 엔티티 간 관계를 따라 검색한다.
   - 여러 문서에 흩어진 사실을 연결해야 하는 질문에 강하다.

2. Agentic RAG / CRAG
   - 검색 결과를 그대로 믿지 않고 먼저 관련성을 채점한다.
   - 부족하면 질문을 다시 쓰고 재검색하거나 fallback으로 보정한다.

> 오늘의 핵심 문장: 비슷한 조각만 찾지 말고, 관계를 잇고 검색 결과를 검증하자.

---

### 1. GraphRAG란?

- 기존 벡터 RAG는 질문과 의미가 비슷한 문서 조각을 찾아온다.
- 하지만 "A와 B는 어떤 관계인가?", "여러 문서에 흩어진 정보를 연결해 설명해줘" 같은 질문에는 약할 수 있다.
- GraphRAG는 문서에서 엔티티와 관계를 추출해 지식 그래프를 만들고, 그 그래프를 따라 검색하는 방식이다.

| 구분 | 벡터 RAG | GraphRAG |
|---|---|---|
| 검색 단위 | 텍스트 청크 | 엔티티와 관계 |
| 기준 | 의미 유사도 | 연결 관계와 경로 |
| 강점 | 단일 문서 설명, 의미 검색 | 관계 질문, 추론, 전역 요약 |
| 약점 | 흩어진 사실 연결에 약함 | 그래프에 없는 사실은 찾기 어려움 |

---

### 2. 벡터 RAG가 약한 질문

- 벡터 검색은 한 조각 안에 답이 들어 있는 질문에는 강하다.
- 하지만 여러 사실을 이어야 하는 질문에는 약할 수 있다.

예시:

- A의 멘토가 다니는 회사는?
- 이 프로젝트 담당자의 상사는?
- 이순신이 머문 바다와 관련된 전투는?
- 여러 문서 전체의 핵심 주제는?

이런 질문은 한 문서 조각만으로 답이 나오지 않고, 여러 정보를 연결해야 한다.

---

### 3. 지식 그래프와 트리플

- 지식 그래프는 세상을 점과 선으로 표현한다.
- 점은 엔티티이고, 선은 관계이다.
- 관계를 표현하는 기본 단위는 트리플이다.

```text
(주어, 관계, 목적어)
```

예시:

```text
(스티브잡스, 설립, 애플)
(이순신, 머문곳, 한산도)
(한산도, 관련전투, 한산도대첩)
(AI휴먼, 사용한다, RAG)
```

트리플이 많이 쌓이면 문서 속 지식이 하나의 관계 지도처럼 바뀐다.

---

### 4. LLM으로 트리플 추출하기

- GraphRAG에서는 문서에서 엔티티와 관계를 추출해야 한다.
- LLM을 사용해 텍스트에서 `(주어, 관계, 목적어)` 형태의 트리플을 뽑을 수 있다.
- 좋은 그래프를 만들려면 프롬프트에서 규칙을 명확히 주는 것이 중요하다.

```python
prompt = """
다음 글에서 (주어, 관계, 목적어) 트리플만 JSON 배열로 뽑아줘.
예: [["스티브잡스","설립","애플"], ["애플","출시","아이폰"]]

글: {text}
"""
```

좋은 추출 규칙:

- 관계는 동사형으로 작성한다.
- 같은 대상은 같은 이름으로 통일한다.
- 추측하지 말고 문서에 있는 사실만 추출한다.
- JSON 형식만 출력한다.

### 5. networkx로 그래프 만들기

- 실습에서는 `networkx`로 간단한 방향 그래프를 만들 수 있다.
- 트리플 하나가 그래프에서 엣지 하나가 된다.
- 주어와 목적어는 노드가 되고, 관계는 엣지 속성이 된다.

```python
import networkx as nx

G = nx.DiGraph()

for s, r, o in triples:
    G.add_edge(s, o, relation=r)

print(G.number_of_nodes())
print(G.number_of_edges())
```

### 6. GraphRAG 검색 흐름

GraphRAG도 최종적으로는 컨텍스트 구성 후 LLM이 답변을 생성한다. 다만 검색 방식이 벡터 검색이 아니라 그래프 탐색이다.

흐름:

1. 질문 속 엔티티를 찾는다.
2. 그래프에서 해당 엔티티를 찾는다.
3. 이웃 노드와 관계를 1~2 hop 정도 탐색한다.
4. 관련 트리플을 문장 형태의 컨텍스트로 바꾼다.
5. LLM이 그 컨텍스트를 근거로 답한다.

예시 컨텍스트:

```text
이순신은 한산도에 머물렀다.
한산도는 한산도대첩과 관련 있다.
```

이렇게 그래프를 따라가면 여러 문서에 흩어진 사실을 연결할 수 있다.

---

### 7. 커뮤니티 요약

- 문서 전체의 큰 주제를 묻는 전역 질문에는 단순 이웃 탐색만으로 부족할 수 있다.
- GraphRAG에서는 그래프를 여러 커뮤니티로 나누고, 각 커뮤니티를 요약해 둔다.
- 전역 질문이 들어오면 커뮤니티 요약들을 모아 답변한다.

흐름:

1. 촘촘히 연결된 노드끼리 커뮤니티로 묶는다.
2. 각 커뮤니티를 LLM으로 요약한다.
3. 전역 질문에는 커뮤니티 요약들을 모아 답변한다.

이 방식은 "문서 전체의 핵심 주제는?" 같은 질문에 유리하다.

---

### 8. 벡터 RAG와 GraphRAG는 함께 써야 한다

- GraphRAG가 벡터 RAG를 대체하는 것은 아니다.
- 두 방식은 잘하는 일이 다르다.

| 방식 | 강한 부분 |
|---|---|
| 벡터 RAG | 원문 표현, 상세 설명, 의미 검색 |
| GraphRAG | 관계, 경로, 추론 질문, 구조 요약 |

실전에서는 두 검색 결과를 함께 가져오고, 필요하면 리랭킹해서 최종 컨텍스트를 구성한다.

---

### 9. GraphRAG의 주의점

| 문제 | 설명 |
|---|---|
| 추출 오류 | LLM이 잘못된 트리플을 만들면 그래프에 그대로 반영됨 |
| 구축 비용 | 문서마다 LLM 호출이 필요해 비용과 시간이 듦 |
| 엔티티 정규화 | 애플, Apple, 애플사 같은 표현이 다른 노드로 갈라질 수 있음 |
| 범위 한계 | 그래프에 없는 사실은 찾을 수 없음 |
| 검증 필요 | 잘못된 관계가 답변 오류로 이어질 수 있음 |

GraphRAG의 원칙:

> 추출은 검증하고, 엔티티는 통합하고, 그래프에 없는 정보는 벡터 검색으로 보완한다.

---

### 10. Agentic RAG란?

- 기본 RAG는 검색 결과를 그대로 믿고 답변한다.
- 검색 결과가 틀리거나 부족하면 LLM이 그럴듯한 답을 만들 수 있다.
- Agentic RAG는 검색 결과를 먼저 평가하고, 부족하면 행동을 바꾸는 RAG이다.

가능한 행동:

- 관련 문서만 골라 답변 생성
- 질문을 다시 써서 재검색
- 외부 검색 또는 보조 지식 사용
- 근거가 없으면 모른다고 답변

> Agentic RAG의 핵심은 검색 결과를 믿지 말고 일단 채점하라는 것이다.

---

### 11. CRAG란?

- CRAG는 Corrective RAG의 약자이다.
- 검색 결과를 채점하고, 부족하면 보정하는 구조이다.

흐름:

1. 질문을 받는다.
2. 문서를 검색한다.
3. LLM grader가 문서 관련성을 판단한다.
4. 관련 문서가 있으면 그 문서만으로 답변한다.
5. 관련 문서가 없으면 질문을 재작성한다.
6. 재검색한다.
7. 반복해도 실패하면 fallback으로 이동한다.
8. 최종적으로 답변하거나 모른다고 말한다.

---

### 12. LLM Grader

- LLM grader는 검색된 각 문서가 질문에 답하는 데 관련이 있는지 판단한다.
- 보통 `yes` 또는 `no`로 판단하게 만든다.

```python
prompt = f"""
다음 문서가 질문에 답하는 데 관련이 있는지 판단하라.
오직 yes 또는 no 한 단어로만 답하라.

[문서]
{doc}

[질문]
{question}

[판정]
"""
```

판정 결과:

- `yes`가 하나라도 있으면 관련 문서만 모아 답변 생성
- 모두 `no`면 검색 실패로 보고 재작성 단계로 이동

주의할 점:

- LLM이 꼭 `yes`만 출력하지 않을 수 있다.
- 예: `Yes, 관련 있습니다.`처럼 답할 수 있으므로 파싱을 견고하게 해야 한다.

---

### 13. 질문 재작성

- 검색이 실패했을 때 같은 질문으로 다시 검색하면 같은 결과가 나올 가능성이 크다.
- 따라서 질문을 검색 친화적으로 다시 써야 한다.

예시:

```text
원본 질문: 이텍텍 채용 공고 있어?
재작성 질문: 이텍텍 채용 모집 직군 지원 공고
```

재작성 전략:

- 핵심 키워드 중심으로 바꾸기
- 모호한 표현 제거
- 동의어 추가
- 검색에 잘 걸리는 명사형 표현으로 바꾸기

중요한 점은 원본 질문의 의도를 보존해야 한다는 것이다.

---

### 14. Fallback

- 재작성과 재검색을 여러 번 해도 답을 찾지 못하면 fallback을 사용한다.
- fallback은 최후의 수단이어야 한다.

서비스에서 가능한 fallback:

- 웹 검색 API
- 다른 지식베이스
- 관리자 확인 요청
- "제공된 자료로는 확인할 수 없습니다"라고 답변

fallback을 너무 쉽게 사용하면 비용과 외부 의존성이 커진다.

---

### 15. Self-RAG와 CRAG 차이

- Self-RAG는 모델이 자기 평가 토큰을 사용해 검색 필요 여부와 답변 품질을 스스로 판단하는 방식이다.
- CRAG는 별도 grader 또는 그래프 노드가 검색 결과를 평가한다.

Self-RAG 예시 토큰:

- `[Retrieve]`: 검색이 필요한가?
- `[IsRel]`: 가져온 문서가 관련 있는가?
- `[IsSup]`: 답변이 문서로 뒷받침되는가?
- `[IsUse]`: 답변이 유용한가?

| 구분 | CRAG | Self-RAG |
|---|---|---|
| 판단 주체 | 외부 grader 또는 그래프 노드 | 생성 모델 자신 |
| 구현 난이도 | 낮음 | 높음 |
| 필요 조건 | 범용 LLM으로 가능 | 전용 학습 또는 특수 구조 필요 |
| 실습 적합성 | 좋음 | 개념 학습 중심 |

---

### 16. LangGraph에서 CRAG 구현 핵심

- CRAG는 분기와 루프가 필요하므로 LangGraph와 잘 맞는다.
- 상태 설계가 중요하다.

중요한 상태:

- `question`: 현재 검색 질문
- `original_question`: 사용자의 원래 질문
- `documents`: 검색된 문서
- `graded_documents`: 관련 있다고 판단된 문서
- `tries`: 재작성 횟수
- `MAX_TRIES`: 최대 재시도 횟수

종료 조건은 반드시 있어야 한다.

```python
MAX_TRIES = 2

if has_relevant_docs:
    route = "generate"
elif state["tries"] < MAX_TRIES:
    route = "rewrite"
else:
    route = "fallback"
```

### 17. CRAG에서 자주 생기는 실수

| 실수 | 문제 |
|---|---|
| grader 파싱을 너무 엄격하게 함 | `Yes, 관련 있습니다` 같은 답을 처리하지 못함 |
| END 경로 누락 | 그래프가 멈추지 않거나 오류 발생 |
| tries 카운터 없음 | 재작성 루프가 무한 반복됨 |
| fallback 남용 | 비용과 외부 의존성이 커짐 |
| 원래 질문 분실 | 재작성 질문 기준으로 답해 사용자 의도와 어긋남 |
| 상태 전체 반환 | LangGraph 상태 병합이 꼬일 수 있음 |

CRAG의 원칙:

> 검색 결과를 채점하고, 부족하면 고치고, 그래도 없으면 정직하게 모른다고 말한다.

---

### 18. 통합 관점

GraphRAG와 Agentic RAG는 서로 다른 문제를 해결한다.

| 문제 | 해결 방식 |
|---|---|
| 여러 문서에 흩어진 사실을 이어야 함 | GraphRAG |
| 엔티티 간 관계를 따라가야 함 | GraphRAG |
| 검색 결과가 관련 있는지 불확실함 | CRAG |
| 검색 실패 후 다시 시도해야 함 | CRAG |
| 환각을 줄이고 싶음 | CRAG |
| 지식 구조와 검색 품질을 모두 잡고 싶음 | GraphRAG + CRAG |

실전 RAG 구성:

1. 질문을 받는다.
2. 벡터 검색과 그래프 검색을 함께 수행한다.
3. 검색 결과를 LLM grader로 평가한다.
4. 충분하면 답변을 생성한다.
5. 부족하면 질문을 재작성해 재검색한다.
6. 그래도 없으면 fallback 또는 확인 불가 답변을 낸다.

> 좋은 RAG는 단순히 검색하는 시스템이 아니라, 관계를 이해하고 검색 결과를 의심하며 부족하면 스스로 보정하는 시스템이다.

## 오늘의 회고

### 배운 점

- 벡터 RAG는 의미가 비슷한 문서 조각을 찾는 데 강하지만 관계와 추론 질문에는 약할 수 있다.
- GraphRAG는 문서를 엔티티와 관계로 바꾸어 흩어진 사실을 연결하는 검색 방식이다.
- 지식 그래프는 `(주어, 관계, 목적어)` 형태의 트리플을 쌓아 만든다.
- LLM을 이용하면 문서에서 트리플을 추출할 수 있지만, 추출 오류와 엔티티 정규화 문제가 생길 수 있다.
- GraphRAG는 벡터 RAG를 대체하는 것이 아니라 보완하는 방식이다.
- Agentic RAG는 검색 결과를 그대로 믿지 않고 관련성을 판단한 뒤 행동을 바꾸는 구조이다.
- CRAG는 검색, 채점, 재작성, 재검색, fallback 흐름으로 환각을 줄인다.
- LangGraph를 사용할 때는 루프 종료 조건과 상태 관리가 매우 중요하다.

### 어려운 점 / 개선할 점

- 트리플 추출 품질이 그래프 품질을 결정하므로 프롬프트 설계가 중요하다.
- 같은 엔티티가 여러 이름으로 갈라지는 문제를 어떻게 정규화할지 고민이 필요하다.
- 그래프 검색 결과와 벡터 검색 결과를 어떻게 합칠지 설계가 필요하다.
- LLM grader는 `yes/no`만 요구해도 다양한 문장으로 답할 수 있어 파싱을 견고하게 해야 한다.
- 재작성 루프에는 반드시 `tries`와 `MAX_TRIES`가 있어야 한다.
- fallback은 유용하지만 남용하면 비용과 외부 의존성이 커진다.

---

## 액션 플랜

- 작은 문서셋에서 LLM으로 트리플을 추출해본다.
- 추출한 트리플을 `networkx` 그래프로 저장한다.
- 특정 엔티티 기준으로 1~2 hop 이웃을 탐색해 서브그래프를 만들어본다.
- 그래프에서 가져온 트리플을 문장형 컨텍스트로 바꿔 LLM 답변에 넣어본다.
- 벡터 검색 결과와 그래프 검색 결과를 비교한다.
- 검색된 문서에 대해 LLM grader로 `yes/no` 관련성 평가를 해본다.
- 관련 문서가 없을 때 질문 재작성 후 재검색하는 루프를 구현한다.
- LangGraph에서 `tries` 카운터와 `MAX_TRIES` 종료 조건을 넣는다.
- fallback 시 "자료로는 확인할 수 없음"을 명확히 말하는 답변을 만든다.

## 함께 나누고 싶은 점

- RAG는 단순히 문서를 검색해 답하는 구조에서 점점 더 똑똑한 검색 시스템으로 발전하고 있다.
- GraphRAG는 문서 속 지식을 관계 중심으로 구조화해, 단순 유사도 검색으로 어려운 질문에 대응할 수 있게 한다.
- CRAG는 검색 결과를 무조건 믿지 않고 평가하고 보정함으로써 환각을 줄인다.
- AI 휴먼에 적용하면 사용자의 복잡한 질문에 대해 제공된 자료가 충분한지 확인하고, 부족하면 다시 찾고, 없으면 정직하게 말하는 상담자가 될 수 있다.
- 좋은 RAG는 많이 찾는 것보다 제대로 연결하고 제대로 의심하는 것이 중요하다.

## 한 줄 정리

GraphRAG는 문서 속 지식을 관계 그래프로 연결하고, CRAG는 검색 결과를 평가·보정해 RAG가 더 정확하고 정직하게 답하도록 만드는 구조이다.
