# 2026-07-02 TIL - Advanced RAG와 멀티모달 검색

## 오늘 배운 내용

오늘은 RAG의 검색 정확도를 높이는 방법을 배웠다. 핵심은 단순히 LLM 성능을 올리는 것이 아니라, 좋은 근거를 잘 찾아오도록 검색 단계를 개선하는 것이다.

오늘 배운 내용은 크게 세 가지이다.

- Advanced Retrieval: 기본 벡터 검색의 한계를 보완하는 검색 강화 기법
- 한국어 임베딩과 청킹: 한국어 문장을 제대로 벡터화하고 문서를 검색하기 좋은 크기로 나누는 전략
- 멀티모달 RAG: 텍스트뿐 아니라 그림, 표, 차트, 스캔 문서까지 검색하고 답변하는 구조

> 오늘의 핵심 문장: 검색을 잘해야 RAG가 산다.

---

### 1. Advanced Retrieval

- 기본 벡터 검색은 의미 기반 검색에는 강하지만 모든 상황에서 좋은 결과를 주지는 않는다.
- 고유명사, 모델명, 코드, 숫자처럼 정확한 문자 매칭이 중요한 경우에는 벡터 검색만으로 부족할 수 있다.
- 관련 문서를 찾았더라도 진짜 정답이 뒤쪽에 있으면 LLM에 좋은 근거가 전달되지 않을 수 있다.
- 질문이 짧거나 모호하면 검색 쿼리 자체가 약해져 검색 결과가 나빠질 수 있다.

| 문제 | 설명 | 처방 |
|---|---|---|
| 고유명사에 약함 | 모델명, 코드, 숫자처럼 정확한 문자열을 놓칠 수 있음 | 하이브리드 검색 |
| 순서가 정답순이 아님 | 관련 문서는 찾았지만 진짜 정답이 뒤에 있을 수 있음 | 리랭킹 |
| 질문이 모호함 | 짧고 애매한 질문은 검색도 애매해짐 | 쿼리 변환 |

---

### 2. 하이브리드 검색

- 하이브리드 검색은 BM25 키워드 검색과 벡터 의미 검색을 함께 사용하는 방식이다.
- BM25는 정확한 단어, 모델명, 코드, 숫자 검색에 강하다.
- 벡터 검색은 동의어, 의미 유사도, 바꿔 말한 표현에 강하다.
- 두 방식을 섞으면 서로의 약점을 보완할 수 있다.

예를 들어 `KEZ8602UH` 같은 모델명은 의미보다 정확한 문자 매칭이 중요하므로 BM25가 유리하다.

```text
최종 점수 = BM25 점수 * weight1 + 벡터 유사도 * weight2
```

---

### 3. 리랭킹

- 리랭킹은 1차 검색으로 후보를 넓게 가져온 뒤, 2차 모델이 다시 정밀하게 순위를 매기는 방식이다.
- 1차 검색은 후보를 20~30개 정도 넓게 가져온다.
- reranker가 질문과 문서의 관련도를 다시 계산한다.
- 최종적으로 상위 5개 정도만 LLM에 전달한다.
- 한국어에서는 `bge-reranker-v2-m3` 같은 다국어/한국어 리랭커를 사용할 수 있다.

```text
질문 -> 1차 검색 Top-30 -> reranker 재정렬 -> Top-5 -> LLM 답변
```

---

### 4. 쿼리 변환

- 검색 실패 원인이 질문 자체에 있을 때 사용한다.
- 사용자의 질문을 검색하기 좋은 형태로 바꾸거나 여러 개로 나누는 방식이다.

| 방식 | 설명 |
|---|---|
| Multi-Query | 하나의 질문을 여러 표현으로 바꿔 검색 |
| HyDE | 가상의 모범 답안을 먼저 만들고 그 답안을 검색 쿼리처럼 사용 |
| 질문 분해 | 여러 주제가 섞인 질문을 작은 질문들로 나눔 |

예시 질문:

```text
PERSO AI로 아바타 만들고 말투까지 설정하려면?
```

분해:

```text
1. PERSO AI에서 아바타를 어떻게 생성하나?
2. 페르소나 말투는 어떻게 설정하나?
```

---

### 5. 한국어 임베딩

- 임베딩은 문장을 숫자 벡터로 바꾸는 과정이다.
- RAG 검색은 질문 벡터와 가장 가까운 문서 벡터를 찾는 과정이므로 임베딩 품질이 검색 품질에 직접 영향을 준다.
- 영어 임베딩 모델을 한국어에 그대로 쓰면 한국어 의미 관계를 잘 못 잡을 수 있다.
- 한국어는 조사와 어미 변화가 많아 토큰화 방식의 영향을 크게 받는다.

한국어 RAG에서는 한국어 또는 다국어 검색에 강한 임베딩 모델을 쓰는 것이 중요하다.

| 모델 | 특징 |
|---|---|
| `BAAI/bge-m3` | 다국어와 한국어 검색에 강함. 무난한 1순위 후보 |
| `multilingual-e5-large` | 다국어 검색용. `query:` / `passage:` 접두어 필요 |
| `nlpai-lab/KoE5` | 한국어 검색 특화 e5 계열. 접두어 필요 |
| `ko-sroberta-multitask` | 한국어 특화, 비교적 가벼움. CPU 환경에도 적합 |

---

### 6. e5 계열 접두어 규칙

- e5 계열 모델은 입력 앞에 역할 접두어를 붙여야 한다.
- 질문에는 `query:`를 붙인다.
- 문서에는 `passage:`를 붙인다.

```text
query: 환불은 어떻게 하나요?
passage: 주문 후 7일 이내 환불 가능합니다.
```

접두어를 빼먹으면 질문과 문서의 벡터 좌표가 어긋나 검색 성능이 떨어질 수 있다.

---

### 7. 한국어 청킹

- 청킹은 긴 문서를 검색하기 좋은 조각으로 나누는 과정이다.
- 문서를 너무 크게 나누면 불필요한 정보가 많아진다.
- 문서를 너무 작게 나누면 맥락이 끊긴다.
- 따라서 적절한 `chunk_size`와 `chunk_overlap`이 필요하다.
- overlap은 보통 chunk_size의 10~20% 정도로 시작한다.
- 한국어 문서는 영어 기준 값을 그대로 쓰기보다 보통 300~800자 범위에서 실험하는 것이 좋다.

| 설정 | 의미 |
|---|---|
| `chunk_size` | 하나의 청크 크기 |
| `chunk_overlap` | 인접 청크끼리 겹치는 부분 |

---

### 8. 청킹 전략

| 전략 | 설명 | 잘 맞는 문서 |
|---|---|---|
| Recursive Character | 문단, 줄, 문장, 단어 순서로 나눔 | 일반 문서, 매뉴얼, 정책 |
| Parent-Document | 작은 자식 청크로 검색하고 큰 부모 청크를 반환 | 계약서, 논문, 긴 가이드 |
| Semantic Chunking | 의미가 바뀌는 지점에서 나눔 | 블로그, 회의록, 주제가 섞인 문서 |

문서별 추천:

- 일반 설명문 / 매뉴얼: Recursive, size 500 / overlap 80
- 계약서 / 논문: Parent-Document, 부모 1500~2000 / 자식 300~400
- 회의록 / 블로그: Semantic Chunking, percentile 80~90
- FAQ / Q&A: 질문-답변 단위로 1청크

---

### 9. 멀티모달 RAG

- 기존 텍스트 RAG는 문서의 글자를 임베딩해 검색한다.
- 하지만 업무 문서에는 그림, 표, 차트, 화면, 스캔 PDF처럼 글자만으로 표현되지 않는 정보가 많다.
- 멀티모달 RAG는 이런 문서를 이미지로 검색하고, VLM이 이미지를 보고 답변하는 구조이다.

텍스트 RAG가 놓치기 쉬운 것:

- 그림 / 다이어그램
- 표 / 차트
- 스캔 PDF
- 레이아웃, 캡션, 박스 위치
- 화면이나 매뉴얼 이미지

OCR을 사용해도 글자만 추출할 뿐, 표 구조, 그래프 모양, 레이아웃 정보는 잃을 수 있다.

---

### 10. CLIP 기반 이미지 검색

- CLIP은 이미지와 텍스트를 같은 벡터 공간에 올리는 모델이다.
- 텍스트 질문으로 관련 이미지를 찾을 수 있다.

흐름:

1. PDF 페이지를 이미지로 변환한다.
2. 각 이미지를 CLIP으로 벡터화한다.
3. 질문을 텍스트 벡터로 변환한다.
4. 코사인 유사도로 관련 이미지 Top-k를 찾는다.
5. 찾은 이미지를 VLM에 넣어 답변을 생성한다.

> 핵심 구조: 이미지로 찾고, VLM이 보고 답한다.

---

### 11. ColPali / ColQwen

- ColPali와 ColQwen은 문서를 OCR이나 텍스트 파싱으로 쪼개지 않고 페이지 이미지를 그대로 색인하는 방식이다.
- 기존 방식은 PDF에서 OCR을 수행하고 텍스트를 추출한 뒤 청킹과 임베딩을 진행한다.
- ColPali 방식은 PDF 페이지를 이미지 그대로 색인하고, 질문과 페이지의 패치 매칭을 수행한다.
- 장점은 글자, 그림, 표 배치 정보를 함께 보존할 수 있다는 점이다.

```text
기존 방식: PDF -> OCR -> 텍스트 추출 -> 청킹 -> 임베딩
ColPali 방식: PDF 페이지 -> 이미지 그대로 색인 -> 질문과 페이지 매칭
```

---

### 12. 텍스트 RAG와 멀티모달 RAG 결합

- 멀티모달 RAG가 텍스트 RAG를 대체하는 것은 아니다.
- 업무에서는 두 방식을 함께 쓰는 것이 좋다.

| 질문 유형 | 적합한 방식 |
|---|---|
| 글자 중심 질문 | 텍스트 RAG |
| 표, 차트, 그림 질문 | 이미지 RAG |
| 최종 답변 | 텍스트 후보 + 이미지 후보를 함께 보고 생성 |

---

### 13. 자주 생기는 실수

Advanced Retrieval:

- 모든 기법을 무조건 붙여서 시스템을 복잡하게 만든다.
- 리랭킹 후보를 너무 적게 줘서 추릴 것이 없다.
- 한국어 문서에 영어 전용 모델을 사용한다.
- BM25와 벡터 검색 weight를 실험하지 않는다.

한국어 임베딩 / 청킹:

- e5 계열에서 `query:` / `passage:` 접두어를 빼먹는다.
- 인덱싱과 검색에 서로 다른 임베딩 설정을 사용한다.
- overlap을 0으로 둬서 문맥이 끊긴다.
- 영어 기준 chunk_size를 그대로 사용한다.
- 청킹 변경 후 평가하지 않는다.

멀티모달 RAG:

- 이미지 임베딩 후 L2 정규화를 빼먹는다.
- 이미지와 텍스트 전처리가 일관되지 않다.
- 페이지 해상도를 너무 낮게 변환한다.
- 검색한 이미지를 VLM에 넣지 않아 환각이 생긴다.
- VLM OOM 상황에 대한 대비가 없다.

---

### 14. 통합 관점

오늘 배운 내용은 하나의 RAG 개선 파이프라인으로 연결된다.

1. 기본 벡터 검색으로 시작한다.
2. 고유명사와 키워드가 중요하면 하이브리드 검색을 사용한다.
3. 검색 결과 순서가 애매하면 리랭킹을 붙인다.
4. 질문이 짧거나 모호하면 Multi-Query, HyDE, 질문 분해를 사용한다.
5. 한국어 문서에는 한국어 임베딩을 사용한다.
6. 문서 성격에 맞게 청킹 전략을 선택한다.
7. 표, 차트, 이미지, 스캔 문서는 멀티모달 RAG로 처리한다.
8. 변경 전후에는 RAGAS나 테스트셋으로 평가한다.

> 좋은 RAG는 LLM 하나로 해결하는 것이 아니라, 검색 단계부터 문서 구조와 언어, 모달리티에 맞게 설계하는 것이다.

## 오늘의 회고

### 배운 점

- RAG 품질은 LLM보다 검색 결과가 크게 좌우한다.
- 기본 벡터 검색은 의미 검색에는 강하지만 고유명사와 코드에는 약할 수 있다.
- 하이브리드 검색은 BM25와 벡터 검색을 결합해 키워드와 의미 검색의 장점을 함께 사용한다.
- 리랭킹은 넓게 가져온 후보를 다시 정밀하게 추려 LLM에 좋은 근거를 전달한다.
- 쿼리 변환은 질문 자체를 검색하기 좋은 형태로 바꾸는 방법이다.
- 한국어 RAG에서는 한국어에 맞는 임베딩 모델과 청킹 전략이 필요하다.
- 멀티모달 RAG는 텍스트뿐 아니라 그림, 표, 차트, 스캔 문서까지 검색 대상으로 확장한다.
- 텍스트 RAG와 이미지 RAG는 대체 관계가 아니라 보완 관계다.

### 어려운 점 / 개선할 점

- 검색 실패 원인을 먼저 진단하고, 증상에 맞는 기법을 골라야 한다.
- BM25와 벡터 검색의 비율은 실제 데이터로 튜닝해야 한다.
- e5 계열 접두어 규칙은 모델마다 확인해야 한다.
- `chunk_size`와 `chunk_overlap`은 정답이 없어서 직접 실험해야 한다.
- VLM은 작은 글자를 잘못 읽을 수 있으므로 검증이 필요하다.
- 멀티모달 RAG는 이미지 처리, 해상도, 메모리 관리까지 고려해야 한다.

---

## 액션 플랜

- 기본 벡터 검색과 하이브리드 검색 결과를 비교한다.
- 고유명사 질문에서 BM25 비중을 높였을 때 효과를 확인한다.
- 1차 후보 개수를 5, 20, 30개로 바꿔 리랭킹 결과를 비교한다.
- 짧고 모호한 질문에 Multi-Query와 HyDE를 적용한다.
- `bge-m3`와 `KoE5`로 한국어 검색 결과를 비교한다.
- e5 접두어 유무에 따른 검색 성능 차이를 확인한다.
- `chunk_size` 300, 500, 800을 비교한다.
- overlap 0과 50~80 설정을 비교한다.
- PDF 페이지를 이미지로 변환하고 CLIP으로 검색해본다.
- 검색된 이미지를 VLM에 넣어 근거 답변을 생성한다.
- 모든 변경은 RAGAS나 테스트셋으로 평가한다.

---

## 함께 나누고 싶은 점

- RAG는 문서를 넣고 질문하는 단순 기능이 아니라, 검색 가능한 형태로 문서를 다시 설계하는 과정에 가깝다.
- 한국어 RAG에서는 영어권 기본 설정을 그대로 쓰면 성능이 잘 나오지 않을 수 있다.
- 실제 업무 문서에는 표, 그림, 차트, 스캔본이 많기 때문에 멀티모달 RAG의 적용성이 크다.
- AI 휴먼과 연결하면 사용자가 "이 표 설명해줘" 또는 "매뉴얼에서 관련 그림 찾아줘"라고 말했을 때 관련 페이지를 찾아 보여주고 음성으로 설명할 수 있다.
- 좋은 RAG는 모델 하나가 아니라 데이터의 언어와 문서 형태에 맞는 검색 설계에서 나온다.
