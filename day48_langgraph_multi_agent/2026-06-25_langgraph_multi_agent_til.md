# 2026-06-25 TIL - LangGraph 멀티에이전트와 에이전트 패턴

## 오늘 배운 내용

### 1. LangGraph 멀티에이전트

- 하나의 LLM에게 조사, 작성, 검수, 말투 조정까지 모두 맡기면 프롬프트가 비대해진다.
- 한 모델 안에서 여러 역할이 섞이면 역할 충돌이 생길 수 있다.
- 복잡한 작업은 리서처, 작가, 검수자처럼 역할을 나누는 멀티에이전트 구조가 더 적합하다.
- LangGraph에서는 `State`, `Node`, `Edge`를 이용해 여러 에이전트가 하나의 공유 State에 결과를 누적하며 협업한다.

```text
사용자 요청 -> 리서처 -> 작가 -> 검수자 -> 최종 답변
```

---

### 2. 멀티에이전트 4대 패턴

- 파이프라인은 리서처 -> 작가 -> 검수자처럼 단계적으로 처리하는 구조이다.
- Supervisor는 관리자가 요청 유형을 판단해 질문답변, 요약, 번역 등 알맞은 전문가에게 라우팅하는 구조이다.
- 병렬 처리는 여러 에이전트가 동시에 작업하고 마지막에 결과를 취합하는 구조이다.
- 토론·검증은 서로 다른 입장의 에이전트가 주장과 반론을 주고받고, 최종 판단자가 결론을 내는 구조이다.

| 패턴 | 핵심 |
|---|---|
| 파이프라인 | 정해진 순서대로 역할을 이어서 수행 |
| Supervisor | 관리자 노드가 적절한 전문가에게 라우팅 |
| 병렬 처리 | 여러 결과를 동시에 만들고 취합 |
| 토론·검증 | 주장, 반론, 판단을 분리해 품질 검증 |

---

### 3. 공유 State의 중요성

- 공유 State는 여러 에이전트가 함께 보는 공동 작업 노트와 같다.
- 각 노드는 State 전체를 반환하는 것이 아니라, 자신이 변경한 키만 `dict` 형태로 반환해야 한다.
- State 전체를 덮어쓰면 다른 에이전트가 만든 결과나 `revisions` 카운터가 사라질 수 있다.
- 수정 루프를 만들 때는 반드시 `MAX_REVISIONS` 같은 종료 조건이 필요하다.

```python
def writer_node(state):
    draft = make_draft(state["research"])
    return {"draft": draft}
```

---

### 4. 에이전트 하네스

- LLM은 엔진이고, 하네스는 차체·운전석·브레이크·계기판·안전벨트 역할을 한다.
- LLM 하나만으로는 외부 정보를 가져오거나 도구를 실행하거나 여러 단계를 스스로 반복하기 어렵다.
- 하네스는 목표 입력, 계획, 도구 호출, 관찰, 종료 조건, 로깅, 가드레일을 담당한다.
- 실제 서비스에서는 모델 자체보다 하네스 설계가 안정성을 크게 좌우한다.

---

### 5. ReAct 루프

- ReAct는 Reason과 Act의 결합이다.
- 기본 흐름은 생각 -> 행동 -> 관찰 -> 반복 구조이다.
- LLM이 지금 무엇을 해야 할지 판단하고, 필요한 도구를 호출한다.
- 도구 실행 결과를 관찰로 받아 다음 행동을 결정한다.
- 최종 답이 준비되거나 `max_steps`에 도달하면 루프를 종료한다.
- 종료 조건이 없으면 도구를 무한히 호출하면서 비용과 시간이 폭발할 수 있다.

```text
Thought -> Action -> Observation -> Thought -> ... -> Final Answer
```

---

### 6. 도구 호출과 가드레일

- 도구는 이름, 설명, 인자 스펙으로 구성된다.
- LLM은 도구 설명을 보고 어떤 도구를 사용할지 판단하므로 도구 설명이 명확해야 한다.
- 등록되지 않은 도구는 실행하지 않는 화이트리스트가 필요하다.
- 예약, 결제, 파일 삭제처럼 되돌리기 어려운 행동은 사용자 승인 단계를 거쳐야 한다.
- 도구 실패, API 에러, JSON 파싱 실패는 `try/except`, `retry`, `fallback`으로 방어해야 한다.

---

### 7. 관측과 로깅

- 에이전트는 여러 단계를 거치기 때문에 블랙박스가 되기 쉽다.
- 어떤 스텝에서 어떤 도구를 어떤 인자로 호출했는지 로그로 남겨야 한다.
- 도구 실행 결과가 무엇이었는지도 기록해야 한다.
- 로깅이 있어야 비용, 오류, 도구 선택 실패, 무한루프 원인을 추적할 수 있다.

```text
step=2 tool=search args={"query": "..."} status=success tokens=...
```

---

### 8. 고급 에이전트 패턴

- 단순 ReAct는 한 단계씩만 판단하기 때문에 긴 작업에서는 길을 잃거나 오류가 누적될 수 있다.
- 이를 보완하기 위해 Reflexion, Plan-and-Execute, Tree of Thoughts, 검증 루프 같은 고급 패턴을 사용한다.
- 핵심은 한 번에 끝내지 않고, 계획하고, 되돌아보고, 여러 갈래를 비교하고, 검증하는 것이다.

---

### 9. Reflexion

- Reflexion은 초안을 만든 뒤 스스로 비판하고, 그 비판을 반영해 다시 답을 개선하는 구조다.
- 글쓰기, 요약, 번역, 코드 디버깅처럼 품질을 한 단계 올리고 싶을 때 유용하다.
- 반복 상한이 없으면 무한 교정에 빠질 수 있으므로 `MAX_ITERS` 같은 제한이 필요하다.

```text
초안 생성 -> 자기비판 -> 개선 답변 -> 필요하면 반복
```

---

### 10. Plan-and-Execute

- Plan-and-Execute는 시작 전에 전체 계획을 세우고, 이후 각 단계를 실행하는 방식이다.
- 짧은 작업은 ReAct가 빠르다.
- 다단계 리서치나 여러 도구 조합이 필요한 작업은 Plan-and-Execute가 더 안정적이다.
- 계획이 틀릴 수 있기 때문에 실행 결과를 보고 재계획하는 구조가 필요하다.

---

### 11. Tree of Thoughts

- Tree of Thoughts는 하나의 생각 흐름만 따라가는 것이 아니라, 여러 후보 생각을 펼치고 평가한 뒤 좋은 경로를 선택하는 방식이다.
- 퍼즐, 수학, 기획처럼 첫 직관이 틀리기 쉬운 문제에 강하다.
- 다만 갈래 수와 깊이만큼 LLM 호출이 늘어나므로 비용이 크다.

---

### 12. 검증 루프

- 검증 루프는 생성된 답을 바로 내보내지 않고, 규칙, 도구, 다른 LLM으로 검증한 뒤 통과한 답만 출력하는 구조이다.
- JSON 스키마, 계산 정확성, 정책 준수, 민감정보 필터링처럼 정확성이 중요한 작업에 적합하다.
- 불합격하면 피드백을 반영해 다시 생성한다.
- 이때도 반복 상한이 필요하다.

## 오늘의 회고

### 배운 점

- 단일 LLM 호출만으로는 복잡한 작업을 안정적으로 처리하기 어렵고, 역할 분담과 흐름 제어가 필요하다는 점을 배웠다.
- LangGraph의 `State`, `Node`, `Edge` 구조가 단순한 그래프 개념이 아니라 멀티에이전트 협업의 기반이라는 점이 인상적이었다.
- 에이전트는 LLM 자체보다 하네스, 종료 조건, 도구 호출, 로깅, 가드레일이 더 중요하다는 것을 알게 되었다.
- ReAct, Reflexion, Plan-and-Execute, Tree of Thoughts는 모두 한 번에 답하지 않고 더 잘 생각하게 만드는 구조라는 공통점이 있다.

### 어려운 점 / 개선할 점

- State를 어떻게 설계해야 노드 간 결과가 충돌하지 않는지 더 연습이 필요하다.
- 라우터 반환값과 실제 노드명이 다르면 바로 오류가 날 수 있어 이름 관리가 중요하다.
- 멀티에이전트와 고급 패턴은 품질을 높일 수 있지만, 호출 수가 늘어나 비용과 지연이 커진다.
- 무조건 복잡하게 만들기보다, 나눠야 할 이유가 있을 때만 멀티에이전트 구조를 써야 한다.

## 액션 플랜

- 리서처 -> 작가 -> 검수자 형태의 간단한 파이프라인 그래프를 직접 구현해본다.
- 검수자가 반려하면 작가 노드로 되돌아가는 수정 루프를 만들어본다.

- ReAct 루프에서 `steps` 카운터와 `max_steps` 종료 조건을 반드시 넣어본다.
- Reflexion 루프를 구현해 초안, 자기비판, 개선 답변이 어떻게 달라지는지 확인한다.
