# 2026-06-23 TIL - 스트리밍 음성 AI와 저지연 응답 구조

## 오늘 배운 내용

### 1. 스트리밍과 저지연 응답 구조

- LLM은 답변을 한 번에 완성하는 것이 아니라 토큰을 하나씩 순서대로 생성한다.
- 이 과정은 크게 `Prefill`과 `Decode`로 나뉜다.
- `Prefill`은 질문과 프롬프트 전체를 모델이 읽어들이는 시간이다.
- 입력이 길수록 `Prefill` 시간이 길어지고, 첫 토큰이 늦게 나온다.
- `Decode`는 이후 토큰을 하나씩 생성하는 단계이다.
- `Decode` 속도는 초당 토큰 수인 `TPS`로 측정할 수 있다.
- 사용자가 느끼는 체감 속도는 전체 답변 시간보다 첫 토큰이 나오는 시간인 `TTFB`에 크게 좌우된다.
- 따라서 답변 전체를 기다리지 않고, 토큰이 생성되는 즉시 흘려보내는 스트리밍 방식이 중요하다.
- 특히 음성 AI에서는 첫 반응 시간과 첫 음성 발화 시각이 사용자 경험에 큰 영향을 준다.

```text
사용자 질문 -> Prefill -> 첫 토큰 TTFB -> Decode -> 토큰 스트리밍 -> 답변 완성
```

---

### 2. 문장 단위 TTS와 실시간 음성 에이전트

- 음성 AI는 `STT -> LLM -> 문장 버퍼 -> TTS 재생` 흐름으로 동작한다.
- LLM이 뒤 문장을 계속 생성하는 동안, 앞 문장은 이미 TTS로 합성되어 재생될 수 있다.
- 핵심은 각 단계를 순차적으로 기다리는 것이 아니라 겹쳐서 실행하는 것이다.
- 토큰을 글자 하나씩 TTS로 넘기면 발음이 끊기고 비용과 지연이 커진다.
- 따라서 TTS에는 문장 단위로 모아서 넘기는 방식이 적절하다.
- 한국어 문장 분리는 `.`, `!`, `?`, `...` 같은 종결 부호를 기준으로 할 수 있다.
- 다만 소수점, 약어, 번호 등은 문장 끝이 아닐 수 있으므로 예외 처리가 필요하다.
- STT는 Whisper를 사용할 수 있다.
- 한국어 STT에서는 `language="korean"`, `task="transcribe"` 옵션을 지정하는 것이 중요하다.
- TTS는 `facebook/mms-tts-kor` 같은 모델을 사용할 수 있다.
- TTS 출력 샘플레이트를 정확히 맞춰야 음성이 정상 속도로 재생된다.

```text
STT -> LLM token stream -> sentence buffer -> TTS synthesize -> audio playback
```

---

### 3. 스트리밍 구현에서 중요한 개념

- `TextIteratorStreamer`를 사용하면 LLM이 생성하는 텍스트를 반복자 형태로 받을 수 있다.
- LLM 생성은 별도 스레드에서 실행하고, 메인 흐름은 streamer에서 토큰을 하나씩 꺼내 처리할 수 있다.
- Python `Queue`는 생성된 문장을 TTS 작업으로 넘길 때 사용할 수 있다.
- `asyncio.gather`는 검색, 검증, 도구 호출처럼 동시에 가능한 작업을 병렬로 실행할 때 유용하다.
- 백프레셔는 뒤쪽 처리 단계가 느릴 때 앞쪽 생성 속도를 조절해야 하는 문제이다.
- 실시간 음성 에이전트에서는 LLM 속도, TTS 합성 속도, 오디오 재생 속도 사이의 균형이 중요하다.
- SSE는 서버에서 클라이언트로 텍스트 스트림을 보내는 단방향 구조에 적합하다.
- WebSocket은 음성 입력, 오디오 청크, 끼어들기 처리처럼 양방향 통신이 필요한 경우에 적합하다.

## 핵심 개념 정리

| 개념 | 정리 |
|---|---|
| `Prefill` | 입력 프롬프트 전체를 모델이 읽어 첫 토큰을 준비하는 단계 |
| `Decode` | 이후 토큰을 하나씩 생성하는 단계 |
| `TTFB` | Time To First Byte 또는 첫 토큰이 나오기까지 걸리는 시간 |
| `TPS` | Tokens Per Second, 초당 생성 토큰 수 |
| 스트리밍 | 결과 전체를 기다리지 않고 생성되는 즉시 전송하는 방식 |
| 문장 버퍼 | 토큰을 모아 문장 단위로 TTS에 넘기기 위한 임시 저장 구조 |
| STT | 음성을 텍스트로 변환하는 Speech To Text |
| TTS | 텍스트를 음성으로 변환하는 Text To Speech |
| SSE | 서버에서 클라이언트로 이벤트 스트림을 보내는 단방향 통신 방식 |
| WebSocket | 클라이언트와 서버가 양방향으로 데이터를 주고받는 통신 방식 |
| KV Cache | 이전 토큰 계산 결과를 재사용해 디코딩 속도를 높이는 캐시 |
| 백프레셔 | 뒤쪽 처리 단계가 느려 앞쪽 입력을 조절해야 하는 상황 |

## 오늘의 회고

### 배운 점

- 음성 AI에서 중요한 것은 단순히 답변을 잘 만드는 것이 아니라, 사용자가 얼마나 빠르게 반응을 받는다고 느끼는지라는 점을 배웠다.
- `TTFB`, `TPS`, 첫 발화 시각을 따로 측정해야 실제 체감 성능을 개선할 수 있다는 점이 중요했다.
- 전체 답변을 기다린 뒤 TTS를 실행하는 방식보다, 문장이 완성되는 즉시 TTS로 넘기는 구조가 실시간 음성 AI에 더 적합하다는 것을 이해했다.
- 첫 문장은 짧게 만들기, KV 캐시 사용, 병렬 검색, 모델 라우팅, TTS 스트리밍 같은 기법이 저지연 응답을 만드는 핵심이라는 점을 배웠다.
- SSE와 WebSocket의 차이를 정리했다.
- 단순 채팅 스트리밍에는 SSE가 적합하고, 음성 입력, 오디오 청크, 끼어들기 처리에는 WebSocket이 더 적합하다.

### 어려운 점 / 개선할 점

- 스트리밍 구조는 개념은 이해되지만 실제 구현에서는 스레드, 큐, async, 백프레셔 같은 개념이 함께 얽혀 있어 복잡하게 느껴졌다.
- 문장 단위로 끊는 로직도 단순히 마침표 기준으로 처리하면 안 된다.
- 소수점이나 약어 같은 예외를 고려해야 해서 생각보다 섬세한 설계가 필요했다.
- STT와 TTS에서는 샘플레이트, mono 변환, dtype 변환 같은 오디오 처리 기본기를 놓치면 전체 결과가 깨질 수 있다.
- 단순히 모델을 연결하는 것보다, 각 단계의 지연 시간을 측정하고 병목을 찾아 개선하는 습관이 더 필요하다고 느꼈다.

## 액션 플랜

- `TTFB`, `TPS`, 첫 발화 시각, 전체 응답 시간을 `perf_counter`로 직접 측정해본다.
- `invoke` 방식과 `stream` 방식을 같은 질문, 같은 `max_new_tokens` 조건으로 비교해본다.
- LLM 출력 토큰을 문장 버퍼에 모았다가 문장 단위로 TTS에 넘기는 간단한 예제를 구현해본다.
- 한국어 문장 분리 로직에서 소수점, 번호, 말줄임표 예외 처리를 추가해본다.
- Whisper STT 사용 시 `language="korean"`, `task="transcribe"` 옵션을 반드시 넣고 결과 차이를 비교해본다.
- TTS 결과를 STT로 다시 넣어 원문과 의미가 유지되는지 간단한 왕복 테스트를 해본다.

## 함께 나누고 싶은 점

- 음성 AI는 단순히 `STT -> LLM -> TTS`를 연결하는 것이 아니라, 사용자가 사람과 대화하듯 느끼게 만드는 구조가 중요하다는 점이 인상 깊었다.
- 특히 전체 합성을 기다리지 말고, 문장이 되는 즉시 다음 단계로 흘려보낸다는 개념이 실시간 AI 휴먼의 핵심이라고 느꼈다.
- 앞으로 AI 휴먼 서비스를 만들 때는 모델 성능뿐 아니라, 첫 반응 시간과 첫 음성 발화 시간을 반드시 같이 고려해야 할 것 같다.
